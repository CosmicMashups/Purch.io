# 0003: Offline sync engine scope boundary

**Status:** Accepted — implemented in Phase 6.

**Decision:** The full multi-device conflict-resolution sync engine was built in Phase 6: a server-side `SyncedRecord` ledger (`POST /sync`, idempotency-key replay protection, later-timestamp-auto-cancel with retroactive re-flagging for out-of-order arrivals — never a silent drop) plus a client-side `SyncQueueDao`/`SyncCoordinator` that batches `pending_sync_queue` rows to the server on connectivity restore. It exists primarily to serve Cloud-mode branches that can lose connectivity to the cloud for extended periods.

**Rationale:** Local/dedicated-mode devices talk to a server on the same LAN, which stays reachable even during an internet outage (only Xendit-dependent QR Ph payments are affected). The hard multi-day, multi-device conflict scenario is therefore mainly a Cloud-mode concern. The client-side `pending_sync_queue` write-first pattern is built universally as defense-in-depth (a device's own Wi-Fi can drop independently of the LAN server's health), regardless of deployment mode.

**Boundary — deliberately not built:** the ledger/queue infrastructure is generic across any `EntityType`/`EntityId` and does not attempt to generically apply arbitrary payloads to arbitrary backend entities (a full per-entity-type command dispatcher, a separate and much larger unspecified problem). More importantly, **no existing feature's live write path (POS checkout, inventory movements, etc.) has been retrofitted to actually write through the offline queue** — every feature built in Phases 1–9 still writes directly to the backend over the network. Phase 6 built the conflict-resolution ledger and the generic queue/drain/review infrastructure that such a retrofit would plug into; doing the retrofit itself (auditing every existing write call site, switching it to queue-first, handling the "was this already applied server-side vs. still local-only" UI states) remains a flagged, unstarted follow-up.
